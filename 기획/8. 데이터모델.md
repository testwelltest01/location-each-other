# 데이터 모델 설계서

## 1. 문서 목적

본 문서는 실시간 위치추적형 픽업 앱의 핵심 데이터 구조를 정의하기 위한 문서이다.  
서비스 내에서 어떤 엔티티(Entity)가 존재하는지, 각 엔티티가 어떤 속성(Attribute)을 가지는지, 엔티티 간 관계(Relationship)는 어떻게 구성되는지를 명확히 정리한다.

본 문서는 다음 목적을 가진다.

- 서비스의 핵심 도메인 데이터를 구조화한다.
- 프론트엔드, 백엔드, 데이터베이스 설계의 공통 기준을 마련한다.
- API 요청/응답 구조 설계의 근거로 활용한다.
- 세션, 참여자, 위치 데이터, 이벤트 로그 간 관계를 일관되게 정의한다.
- MVP 기준에서 반드시 필요한 데이터와 추후 확장 가능한 데이터를 구분한다.

---

## 2. 설계 범위

본 문서는 MVP 기준의 데이터 모델을 우선 정의한다.  
즉, 아래 기능 구현을 중심으로 필요한 데이터만 우선 포함한다.

- 운전자의 픽업 세션 생성
- 탑승자 링크 접속
- 탑승자의 실시간 위치 공유
- 운전자의 실시간 위치 추적 화면 표시
- 세션 상태 관리
- 세션 종료 및 만료 처리
- 위치 갱신 이력 및 주요 이벤트 기록

결제, 즐겨찾기 장소, 회원 등급, 푸시 고도화, 분석용 대시보드 등은 본 문서의 핵심 범위에서 제외한다.

---

## 3. 데이터 모델 설계 원칙

### 3.1 세션 중심 설계

본 서비스의 핵심 단위는 사용자가 아니라 **픽업 세션(Pickup Session)** 이다.  
실시간 위치 공유는 영구적인 관계가 아니라, 짧은 시간 동안만 유지되는 세션성 상호작용이다.

### 3.2 역할 분리 설계

하나의 세션에는 최소 2개의 역할이 존재한다.

- 운전자(Driver)
- 탑승자(Passenger)

사용자 자체의 정체성과 세션 내 역할은 구분하여 다룬다.

### 3.3 상태와 이벤트 분리

세션의 현재 상태는 별도 필드로 관리하고,  
그 상태가 어떻게 바뀌었는지는 이벤트 로그로 남긴다.

### 3.4 실시간 데이터와 기록 데이터 분리

현재 화면에 필요한 최신 위치는 빠르게 조회 가능해야 하고,  
과거 위치 기록은 필요 시 별도로 조회 가능한 구조여야 한다.

즉,

- “지금 위치”를 위한 데이터
- “이전 이동 기록”을 위한 데이터  
  를 동일하게 취급하지 않는다.

### 3.5 개인정보 최소 수집

MVP 단계에서는 픽업 세션 운영에 꼭 필요한 최소한의 데이터만 저장한다.  
특히 위치 데이터는 민감정보에 준하는 성격을 가지므로 저장 범위와 보존 정책을 신중히 설계한다.

---

## 4. 핵심 엔티티 목록

본 서비스의 핵심 엔티티는 다음과 같다.

1. `User`
2. `PickupSession`
3. `SessionParticipant`
4. `LocationPoint`
5. `SessionEvent`
6. `SessionLink`
7. `DevicePermissionStatus`

MVP에서 가장 중요한 엔티티는 다음 4개이다.

- `PickupSession`
- `SessionParticipant`
- `LocationPoint`
- `SessionEvent`

## 5. 엔티티 상세 정의

---

## 5.1 User

### 5.1.1 정의

서비스 사용자의 기본 식별 정보를 저장하는 엔티티.  
MVP에서는 회원가입 기반일 수도 있고, 운전자만 로그인 사용자이며 탑승자는 비회원 링크 진입일 수도 있다.

따라서 `User`는 **서비스 계정 기반 사용자**를 표현하며,  
비회원 탑승자는 별도 참여자 정보로 처리할 수 있다.

### 5.1.2 사용 목적

- 운전자 계정 식별
- 향후 로그인 사용자 관리
- 세션 생성 주체 관리

### 5.1.3 필드 정의

| 필드명                | 타입         | 설명                                    | 필수 여부 |
| --------------------- | ------------ | --------------------------------------- | --------- |
| id                    | UUID         | 사용자 고유 ID                          | 필수      |
| name                  | VARCHAR(100) | 사용자 이름 또는 닉네임                 | 선택      |
| phone_number          | VARCHAR(20)  | 전화번호                                | 선택      |
| profile_image_url     | TEXT         | 프로필 이미지 주소                      | 선택      |
| auth_provider         | VARCHAR(50)  | 로그인 제공자 (kakao, google, apple 등) | 선택      |
| auth_provider_user_id | VARCHAR(255) | 외부 인증 제공자의 사용자 식별값        | 선택      |
| created_at            | DATETIME     | 생성 시각                               | 필수      |
| updated_at            | DATETIME     | 수정 시각                               | 필수      |
| deleted_at            | DATETIME     | 소프트 삭제 시각                        | 선택      |

### 5.1.4 비고

MVP에서 탑승자가 비회원 링크 접속만 한다면,  
`User`는 사실상 운전자 중심 데이터가 될 수 있다.

## 5.2 PickupSession

### 5.2.1 정의

운전자가 탑승자를 픽업하기 위해 생성하는 실시간 위치추적 세션의 중심 엔티티.

### 5.2.2 사용 목적

- 세션 전체 생명주기 관리
- 세션 상태 관리
- 운전자-탑승자 연결
- 실시간 위치 공유의 단위 관리

### 5.2.3 필드 정의

| 필드명               | 타입         | 설명                                 | 필수 여부 |
| -------------------- | ------------ | ------------------------------------ | --------- |
| id                   | UUID         | 세션 고유 ID                         | 필수      |
| driver_user_id       | UUID         | 세션 생성 운전자 ID (`User.id`)      | 필수      |
| status               | VARCHAR(50)  | 세션 현재 상태                       | 필수      |
| title                | VARCHAR(100) | 세션 이름 또는 표시용 제목           | 선택      |
| pickup_note          | TEXT         | 운전자가 탑승자에게 남긴 안내 메시지 | 선택      |
| started_at           | DATETIME     | 실제 실시간 위치 공유 시작 시각      | 선택      |
| completed_at         | DATETIME     | 픽업 완료 시각                       | 선택      |
| cancelled_at         | DATETIME     | 취소 시각                            | 선택      |
| expired_at           | DATETIME     | 만료 시각                            | 선택      |
| max_duration_minutes | INT          | 세션 최대 지속 시간(분)              | 선택      |
| created_at           | DATETIME     | 세션 생성 시각                       | 필수      |
| updated_at           | DATETIME     | 세션 수정 시각                       | 필수      |

### 5.2.4 status 허용값

`PickupSession.status`는 아래 값 중 하나를 가진다.

- `CREATED`
- `LINK_SHARED`
- `PASSENGER_JOINED`
- `LOCATION_PERMISSION_PENDING`
- `LOCATION_SHARING_ACTIVE`
- `LOCATION_SIGNAL_LOST`
- `COMPLETED`
- `CANCELLED`
- `EXPIRED`

### 5.2.5 비고

세션 상태는 항상 서버가 기준이며,  
프론트엔드는 해당 상태에 따라 화면과 기능을 다르게 표시한다.

## 5.3 SessionParticipant

### 5.3.1 정의

하나의 세션에 참여하는 주체를 나타내는 엔티티.  
운전자와 탑승자 모두를 이 엔티티로 관리할 수 있다.

### 5.3.2 사용 목적

- 세션 내 역할 관리
- 운전자/탑승자 구분
- 비회원 참여자 관리
- 접속 상태, 이탈 상태 관리

### 5.3.3 필드 정의

| 필드명       | 타입         | 설명                              | 필수 여부 |
| ------------ | ------------ | --------------------------------- | --------- |
| id           | UUID         | 참여자 고유 ID                    | 필수      |
| session_id   | UUID         | 소속 세션 ID (`PickupSession.id`) | 필수      |
| user_id      | UUID         | 회원 사용자 ID (`User.id`)        | 선택      |
| role         | VARCHAR(20)  | 참여 역할 (`DRIVER`, `PASSENGER`) | 필수      |
| display_name | VARCHAR(100) | 표시 이름                         | 선택      |
| phone_number | VARCHAR(20)  | 참여자 전화번호                   | 선택      |
| joined_at    | DATETIME     | 세션 진입 시각                    | 선택      |
| left_at      | DATETIME     | 세션 이탈 시각                    | 선택      |
| is_active    | BOOLEAN      | 현재 활성 참여 여부               | 필수      |
| created_at   | DATETIME     | 생성 시각                         | 필수      |
| updated_at   | DATETIME     | 수정 시각                         | 필수      |

### 5.3.4 설계 포인트

- 운전자는 보통 로그인 사용자이므로 `user_id`가 존재한다.
- 탑승자는 링크 접속 기반이라면 `user_id` 없이도 참여 가능하다.
- `display_name`은 탑승자 브라우저 진입 시 입력받는 구조로 확장 가능하다.

## 5.4 SessionLink

### 5.4.1 정의

탑승자가 세션에 진입하기 위한 초대 링크 정보를 저장하는 엔티티.

### 5.4.2 사용 목적

- 세션 링크 발급
- 링크 유효성 검증
- 링크 만료 관리
- 잘못된 접근 차단

### 5.4.3 필드 정의

| 필드명          | 타입         | 설명             | 필수 여부 |
| --------------- | ------------ | ---------------- | --------- |
| id              | UUID         | 링크 고유 ID     | 필수      |
| session_id      | UUID         | 연결된 세션 ID   | 필수      |
| token           | VARCHAR(255) | 링크 토큰        | 필수      |
| url             | TEXT         | 공유용 전체 URL  | 필수      |
| expires_at      | DATETIME     | 링크 만료 시각   | 필수      |
| first_opened_at | DATETIME     | 최초 접속 시각   | 선택      |
| last_opened_at  | DATETIME     | 마지막 접속 시각 | 선택      |
| is_revoked      | BOOLEAN      | 수동 폐기 여부   | 필수      |
| created_at      | DATETIME     | 생성 시각        | 필수      |
| updated_at      | DATETIME     | 수정 시각        | 필수      |

### 5.4.4 비고

링크와 세션은 1:1 구조로 시작할 수 있으나,  
향후 재발급 기능을 고려하면 1:N 구조가 더 유연하다.

즉, 하나의 세션에 여러 링크 발급 이력이 존재할 수 있다.

---

## 5.5 LocationPoint

### 5.5.1 정의

세션 참여자의 위치 좌표 갱신 기록을 저장하는 엔티티.

### 5.5.2 사용 목적

- 탑승자의 실시간 위치 추적
- 마지막 유효 위치 표시
- 위치 이력 저장
- 신호 끊김 여부 판단
- 지도 경로 표현용 기초 데이터 확보

### 5.5.3 필드 정의

| 필드명          | 타입          | 설명                  | 필수 여부 |
| --------------- | ------------- | --------------------- | --------- |
| id              | UUID          | 위치 포인트 고유 ID   | 필수      |
| session_id      | UUID          | 소속 세션 ID          | 필수      |
| participant_id  | UUID          | 위치를 보낸 참여자 ID | 필수      |
| latitude        | DECIMAL(10,7) | 위도                  | 필수      |
| longitude       | DECIMAL(10,7) | 경도                  | 필수      |
| accuracy_meters | DECIMAL(8,2)  | 위치 정확도(미터)     | 선택      |
| speed_mps       | DECIMAL(8,2)  | 이동 속도(m/s)        | 선택      |
| heading_degrees | DECIMAL(6,2)  | 진행 방향(도)         | 선택      |
| altitude_meters | DECIMAL(8,2)  | 고도                  | 선택      |
| captured_at     | DATETIME      | 기기에서 측정한 시각  | 필수      |
| received_at     | DATETIME      | 서버 수신 시각        | 필수      |
| is_valid        | BOOLEAN       | 유효 좌표 여부        | 필수      |
| invalid_reason  | VARCHAR(100)  | 무효 처리 사유        | 선택      |
| created_at      | DATETIME      | 저장 시각             | 필수      |

### 5.5.4 설계 포인트

- `captured_at`과 `received_at`은 분리한다.
- 지연된 데이터가 들어오는 경우를 고려해야 한다.
- 실시간 화면용 마지막 위치는 이 테이블에서 매번 계산하지 말고 별도 캐시/요약 구조로 관리하는 것이 좋다.

### 5.5.5 위치 무효 예시

- 정확도 과도하게 낮음
- 비정상 점프 좌표
- 세션 종료 이후 도착한 좌표
- 허용 범위 밖의 잘못된 형식

## 5.6 SessionEvent

### 5.6.1 정의

세션 내에서 발생하는 주요 이벤트를 기록하는 로그 엔티티.

### 5.6.2 사용 목적

- 상태 변경 이력 추적
- 디버깅
- 운영 이슈 분석
- 사용자 행동 흐름 파악
- QA 및 추후 분석 근거 확보

### 5.6.3 필드 정의

| 필드명          | 타입         | 설명                       | 필수 여부 |
| --------------- | ------------ | -------------------------- | --------- |
| id              | UUID         | 이벤트 고유 ID             | 필수      |
| session_id      | UUID         | 소속 세션 ID               | 필수      |
| participant_id  | UUID         | 이벤트 발생 주체 참여자 ID | 선택      |
| event_type      | VARCHAR(100) | 이벤트 종류                | 필수      |
| event_payload   | JSON         | 이벤트 상세 데이터         | 선택      |
| previous_status | VARCHAR(50)  | 이전 세션 상태             | 선택      |
| next_status     | VARCHAR(50)  | 변경 후 세션 상태          | 선택      |
| occurred_at     | DATETIME     | 이벤트 발생 시각           | 필수      |
| created_at      | DATETIME     | 저장 시각                  | 필수      |

### 5.6.4 event_type 예시

- `session_created`
- `link_generated`
- `link_opened`
- `passenger_joined`
- `location_permission_requested`
- `location_permission_granted`
- `location_permission_denied`
- `first_location_received`
- `location_updated`
- `location_signal_lost`
- `location_signal_restored`
- `session_completed`
- `session_cancelled`
- `session_expired`

### 5.6.5 비고

현재 상태는 `PickupSession.status`에 저장하고,  
상태 변경의 히스토리는 `SessionEvent`에 저장한다.

---

## 5.7 DevicePermissionStatus

### 5.7.1 정의

탑승자 디바이스의 위치 권한 상태를 관리하는 엔티티 또는 보조 정보 구조.

### 5.7.2 사용 목적

- 위치 권한 허용 여부 추적
- 권한 거부로 인한 세션 진행 불가 판단
- 권한 요청 이력 관리

### 5.7.3 필드 정의

| 필드명          | 타입        | 설명                                                   | 필수 여부 |
| --------------- | ----------- | ------------------------------------------------------ | --------- |
| id              | UUID        | 권한 상태 ID                                           | 필수      |
| session_id      | UUID        | 소속 세션 ID                                           | 필수      |
| participant_id  | UUID        | 대상 참여자 ID                                         | 필수      |
| permission_type | VARCHAR(50) | 권한 종류 (`LOCATION`)                                 | 필수      |
| status          | VARCHAR(50) | 권한 상태 (`UNKNOWN`, `PROMPTED`, `GRANTED`, `DENIED`) | 필수      |
| prompted_at     | DATETIME    | 권한 요청 시각                                         | 선택      |
| responded_at    | DATETIME    | 사용자 응답 시각                                       | 선택      |
| created_at      | DATETIME    | 생성 시각                                              | 필수      |
| updated_at      | DATETIME    | 수정 시각                                              | 필수      |

### 5.7.4 비고

MVP에서는 이 정보를 `SessionParticipant` 또는 `SessionEvent`에 흡수할 수도 있다.  
다만 권한 단계가 서비스 핵심 병목이므로 분리하면 운영 가시성이 좋아진다.

## 6. 엔티티 간 관계 정의

### 6.1 관계 요약

- `User` 1 : N `PickupSession`
- `PickupSession` 1 : N `SessionParticipant`
- `PickupSession` 1 : N `SessionLink`
- `PickupSession` 1 : N `LocationPoint`
- `PickupSession` 1 : N `SessionEvent`
- `SessionParticipant` 1 : N `LocationPoint`
- `SessionParticipant` 1 : N `SessionEvent`
- `SessionParticipant` 1 : N `DevicePermissionStatus`

### 6.2 관계 설명

#### User ↔ PickupSession

한 명의 운전자는 여러 세션을 생성할 수 있다.  
하나의 세션은 한 명의 생성 운전자에 의해 시작된다.

#### PickupSession ↔ SessionParticipant

하나의 세션에는 최소 2명의 참여자가 존재한다.

- 운전자 1명
- 탑승자 1명

향후 다인 탑승 확장을 고려하면 1:N 구조가 적절하다.

#### PickupSession ↔ LocationPoint

하나의 세션 동안 위치 데이터가 여러 번 저장된다.

#### PickupSession ↔ SessionEvent

세션에서 발생하는 모든 주요 상태 변화 및 행동은 이벤트로 기록된다.

## 8. 정규화 및 저장 전략

### 8.1 정규화 원칙

초기에는 과도한 비정규화보다 명확한 책임 분리를 우선한다.

- 세션 정보는 `PickupSession`
- 참여자 정보는 `SessionParticipant`
- 위치 기록은 `LocationPoint`
- 이벤트 기록은 `SessionEvent`

### 8.2 읽기 성능 고려

다만 실시간 서비스 특성상 다음 정보는 빠르게 조회되어야 한다.

- 세션의 현재 상태
- 현재 활성 탑승자
- 탑승자의 마지막 유효 위치
- 마지막 위치 수신 시각

이 정보는 매번 전체 위치 이력에서 계산하면 비효율적일 수 있으므로,
향후 아래와 같은 요약 필드를 고려할 수 있다.

#### PickupSession에 추가 가능한 요약 필드

- current_passenger_latitude
- current_passenger_longitude
- last_location_received_at
- last_location_accuracy_meters

단, MVP에서는 우선 별도 계산 또는 캐시 방식으로 처리해도 된다.

## 13. 설계상 핵심 판단

이 서비스의 데이터 모델에서 가장 중요한 판단은 다음과 같다.

### 13.1 사용자 중심이 아니라 세션 중심이어야 한다

이 앱은 친구 목록이나 장기 관계를 관리하는 앱이 아니라,
짧게 생성되고 빠르게 종료되는 “실시간 픽업 세션” 중심 앱이다.

### 13.2 위치는 단순 속성이 아니라 시계열 데이터다

탑승자의 위치는 한 번 저장되는 값이 아니라 연속적으로 들어오는 기록이다.
따라서 `User.current_location` 같은 단순 구조로 다루면 안 된다.

### 13.3 현재 상태와 과거 기록을 분리해야 한다

지금 세션이 어떤 상태인지와, 그 상태가 어떻게 바뀌어왔는지는 다른 데이터다.
그래서 `PickupSession.status` 와 `SessionEvent` 를 분리한다.

### 13.4 권한 정보도 핵심 도메인이다

이 앱에서 위치 권한은 단순 OS 권한이 아니라
세션 진행 가능 여부를 가르는 핵심 비즈니스 조건이다.

## 14. 최종 정리

본 서비스의 데이터 모델은 아래 흐름을 중심으로 구성된다.

- 운전자가 세션을 만든다.
- 세션 링크가 발급된다.
- 탑승자가 세션에 참여한다.
- 탑승자의 위치 권한 상태가 결정된다.
- 위치 좌표가 연속적으로 기록된다.
- 세션 이벤트가 누적된다.
- 세션은 완료, 취소, 만료 중 하나로 종료된다.

즉, 본 서비스의 데이터 구조는 단순한 지도 앱 데이터가 아니라
**“실시간 위치 공유가 발생하는 짧은 수명의 픽업 세션”** 을 안정적으로 표현하기 위한 구조이다.

이 문서는 이후 API 명세, DB 테이블 설계, 상태관리, 실시간 통신 설계의 기준 문서로 활용한다.
